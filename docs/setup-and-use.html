Set up and use

Where this runs, the exact commands to set it up, and how a job flows once the crew is cast.

Start here

Where this runs: your machine, your project

You set this up on your own machine, and the crew works inside the project you point it at. There is no server to sign up for, no account with us, and nothing hosted by us that runs your crew. This documentation site is the only hosted part, and it is just pages.

The kit is a library plus one install script. You clone the library once, run the script once, and it copies the crew's skills and personas into the AI assistant you already use — into that assistant's skills folder, on your disk. After that, you open your project in that assistant as you normally would, and the crew is simply there: the coordinator, the specialist seats, and the house rules, working in your repo, on your files.

So the shape is: clone the kit anywhere → install from it once → work in your own projects. The kit folder itself is just the source you installed from; your projects never need to live inside it.

The commands

Set up

You need two things on the machine: git and python3. The install script uses only Python's standard library, and it fetches nothing and executes nothing — it copies files, and prints what it copied.

Step 1 — Get the kit and install the front door

git clone https://github.com/veeresh-bikkaneti/agent-call-sheet.git
cd agent-call-sheet
python3 bootstrap.py --list   # preview the plan — writes nothing
python3 bootstrap.py          # install

A bare run targets Claude Code and copies the front door plus the Rigor core set into ~/.claude/skills. A good run ends with:

Setup complete: 151 files copied, 0 already identical, 0 conflicts.

The script also writes a receipt to ~/.claude/skills/INSTALL-RECEIPT.json — what was installed, from which manifest, and what was not installed (link-only entries are never fetched; the receipt names them). Then start a new session in your assistant and ask it to confirm it can see the crew-orchestrator skill by name, before you rely on it.

Step 3 — Cast a crew (optional, recommended)

Instead of the default core set, you can install a named crew — a coordinator plus the seats for one kind of work. Four ship with the kit:

python3 bootstrap.py --template review-crew
CrewCast it when
review-crewA change, a pull request, or a claim needs an independent check before we call it ready.
build-crewWe have an agreed change to implement, with the build, the tests, and the final check kept as separate seats.
research-crewWe need the landscape mapped, a tool vetted, or an existing codebase understood before deciding.
standing-crewEveryday sessions: memory kept, output shaped for quick reading, claims backed by shown work.

A crew is a small file, so a crew can travel. Export the crew you installed (or any current selection) and bring it back — or hand it to a teammate — like this:

python3 bootstrap.py --template review-crew --export-crew ~/crews/review.json
python3 bootstrap.py --import-crew ~/crews/review.json

Export refuses to overwrite an existing crew file (pass --force to replace it on purpose). Import installs the same files the template did — the receipt records the crew's name and that it came from a file. Full detail, including the Paperclip team export, lives in the crew templates page.

Give the crew a job

Use it

Step 4 — Brief the task

Open your own project in your assistant, in a new session, and brief the job in one message: what you want done, and that the crew should run it. One sentence is worth adding, word for word:

Keep the run status in crew-run.jsonl in this project.

That file is how you will watch the work. While the run is live, the coordinator appends one short JSON line to it each time a seat starts, speaks, blocks, hands off, or finishes — the coordinator reports the lines; a seat does not certify its own status. Three real lines from the kit's own recorded run (front-door/real-run.jsonl, shipped in the kit):

{"agent": "Orchestrator", "task": "Open the fusion run: verify the cast art, extract the PR #17 carry-over list, fuse them into the build checklist", "phase": "BRIEF", "status": "running", "artifact": "hidden_files/animated-board/real-run/build-checklist.md", "say": "Run open. Two seats staffed — art verification and carry-over extraction. The checklist they feed decides what the new board must keep."}
{"agent": "Reality Checker", "task": "Verify the 8 cast portraits: episode-embedded art vs the anime-cast source files, sha256 by sha256", "phase": "GATE", "status": "running", "artifact": "hidden_files/animated-board/real-run/art-verification.md", "say": "Decoding the episode's embedded portraits and hashing the source files. Byte-identical or it doesn't ship."}
{"agent": "Scrum Master", "task": "Fuse the art verdict and the carry-over list into the build checklist for the animated board", "phase": "REPORT", "status": "waiting", "artifact": "hidden_files/animated-board/real-run/build-checklist.md", "say": "Standing by — my inputs are the Checker's verdict and the Architect's list, in that order.", "waiting_on": "Reality Checker art verdict + Architect carry-over list"}

The full field list and the claim rules (who holds a task, what a handoff looks like, how a double-claim gets flagged) are in the run-status contract. You never have to write these lines yourself — the coordinator does — but the file is plain text, and it is the run's permanent record.

Step 5 — Watch it on the crew board

Open front-door/board.html from your kit clone in any browser — double-click it; it is one self-contained file, needs no server, and loads nothing from the network. It opens on the kit's recorded real run so you can learn the controls. Then:

1. Click Load a run-status file and pick your project's crew-run.jsonl (or drag the file onto the page). The board labels it honestly: Loaded file — crew-run.jsonl (source unverified).

2. Press ↺ Replay to play the run line by line, or step with ⏮ / ⏭ and the scrubber. A working character hops; a blocked one shakes and wears a BLOCKED badge; when a task moves between seats, its card flies; a seat's latest line appears as its speech bubble.

3. Click any character to open its panel: what it is doing now, its phase and status, the artifact it is holding, the last thing it said, and what it is waiting on or blocked by.

Is the board live? Honestly: no — and here is how following along works

There is no server and no streaming. The board replays the run file; it does not watch it, and nothing updates on its own while you look at the page.

To follow a run while it is still going: the coordinator keeps appending lines to the run file as the crew works. Click Load a run-status file and pick the same file again — the board re-reads it from the top, new lines included — and replay to the current end. That reload is the follow-along mechanism today.

A dedicated live-watch mode is on the roadmap. Until it ships, we will describe the board as what it is: a replay of the record, not a live feed.

Use cases

Five ways to cast a crew

Use case 1

A dev task

Cast build-crew: the coordinator holds the agreed scope, an architect shapes the approach, builders implement, a tests seat covers the checks, and the Reality Checker gates the result before anyone calls it done. On the board you watch BUILD-phase lines accumulate, task cards fly at each handoff, and the run end at the gate's verdict.

Use case 2

A brainstorm

Cast for viewpoints instead of skills: add the persona seats with python3 bootstrap.py --packs crew-personas, then brief the question and name the seats you want in the room — a product seat, a design seat, a skeptic. Nobody touches code; the run file fills with positions in the DEBATE phase, each seat's say line its current stance, and the deliverable is the decision brief the coordinator writes up at the end.

Use case 3

A research task

Cast research-crew: a lead researcher synthesises the sources, a codebase archaeologist maps what already exists, a tool evaluator vets anything you might adopt, and the checker gates the conclusions — the crew's own routine is "vet before adopt". What you see on the board is the question being broken into survey lines, and the final report separates the landscape from the recommendation.

Use case 4

A PR council of experts

Cast review-crew and point it at the pull request: the reviewer reads for correctness, the evidence seat re-measures whatever the change claims, the security seat attacks it, and the checker — who did none of the work — rules READY or NEEDS WORK. Findings land in buckets (act on / consider / noted / dismissed), never as one blended opinion. Our beginner docs walk through a sample council seat by seat.

Use case 5

A scrum team, collaborating

Cast standing-crew and let it run the daily rhythm: a session-start routine loads the memory and the house rules, work moves on task cards through BRIEF → BUILD → GATE → REPORT, and the standup is the board itself — who holds what, who is blocked, who is waiting on whom, in the run file anyone can replay. Our demo film shows this shape end to end: a five-seat crew working a real pull request while the board keeps the record.
